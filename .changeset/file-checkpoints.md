File checkpoints and a rewind that takes the conversation, the memory and the files back to an earlier message in one operation.

An agent that edits a project changes files with its tools and its shell commands, and going back in the conversation left them as the agent made them. Now a run can take a snapshot of its workspace before every user message, and `cog.rewind()` restores it together with the conversation. Everything is off by default: without `checkpoints` no snapshot is taken, and a rewind restores files only when asked.

Snapshots (types, core, sandbox):

- `LocalWorkspace` implements `snapshot`, `restore`, `listSnapshots`, `deleteSnapshot`, and adds `pruneSnapshots(retention)` and `copySnapshot(id, target)`. Snapshots are content-addressed in `.cogitator/checkpoints`: sha256 blobs for file contents and directory trees, one manifest per snapshot. A file whose size, times, inode and mode did not change since the snapshot before is not read again, and a content or a directory that did not change is stored once, so a snapshot per message stays cheap on a real project (`snapshot.stats` says what was read and stored). Symlinks are recorded as links and never followed, modes are kept, a file that changes while it is read is read again, files over `maxFileBytes` (10 MiB) are skipped and listed in `skipped`. `restore(id, { dryRun })` writes through the workspace's safe placement (a temporary file with `O_NOFOLLOW` renamed over the path), removes what the snapshot did not have, opens for the time it runs a directory of the owner made read-only since (one of another user is refused up front), never touches excluded or skipped paths, checks every content against its hash before it changes anything, refuses with `BUSY` while a command of the workspace runs, and returns what it `restored`, `deleted` and `kept`. `LocalWorkspaceOptions.snapshots` sets `exclude`, `maxFileBytes`, a retention policy (`retain: { count, maxAgeMs }`) and `gcGraceMs` for the mark and sweep collection that `deleteSnapshot` and `pruneSnapshots` run.
- The store is safe to keep and share: it is owner only (`0700` directories, `0600` files), blobs and directories are synced before a manifest names them and a blob is reused only at its stored size, names are kept as they are (`__proto__` included), files are hashed a chunk at a time, unreadable directories are recorded as skipped and protected, a file that keeps changing while read is skipped as `changing` instead of stored torn, and a restore plans every change first, so its dry run lists exactly what it then deletes. A restore keeps files made since that the snapshot could not have kept (over its size limit, unreadable) and always applies the default excludes, a dry run reports `busy` while commands of the workspace run, and stores are released when their workspaces are disposed. Several processes may share a store: snapshots, restores and copies leave markers in `locks/`, a collection takes `locks/gc.lock` and defers its sweep while a marker is there (`gc.deferred`), skips manifests whose trees cannot be read (`gc.unreadable`), and sweeps only the names the store gives in directories checked to be its own, never through a symlink. A failed retention prune no longer fails the snapshot before it, and copies between two stores in opposite directions no longer wait for each other.
- `DockerWorkspace` removes in the container what a restore deletes and refuses with `BUSY` while commands or kept background processes run there, and forwards `restore` with its options, `listSnapshots`, `deleteSnapshot` and `copySnapshot` to its host workspace, and exposes the host as `host`. `RemoteShellWorkspace` (E2B, Daytona, Vercel) keeps its tar snapshots with the same API: `maxFileBytes` and `skipped`, `restore(id, { dryRun })` with the same result (a tar restore rewrites every file it holds, so `restored` lists them all).
- New types: `WorkspaceRestoreOptions`, `WorkspaceRestoreResult` (with `busy` for a dry run), `WorkspaceSnapshotSkip` (`too-large`, `unreadable`, `changing`), `WorkspaceSnapshotStats`, `WorkspaceSnapshot.maxFileBytes`, `WORKSPACE_SNAPSHOT_MAX_FILE_BYTES`, and `Workspace.copySnapshot?`. Remote restores keep directories that hold excluded entries and files over the snapshot's size limit.

Checkpoints and rewind (types, core, config, memory):

- `checkpoints: true | { enabled?, exclude?, maxFileBytes? }` on `CogitatorConfig` (with `rewindFiles?`), `AgentConfig` and `RunOptions`: a run whose workspace can snapshot takes `workspace.snapshot({ label: entryId })` before every user message it writes (the input and queued `steer`, `followUp` and `inject` messages) and names it in the entry, `metadata.fileCheckpoint` (`FILE_CHECKPOINT_KEY`, `FileCheckpointRef`, `fileCheckpointOf()`). The entry id is known before the entry is written, as `NewMemoryEntry` takes an `id` now. Changes made by shell commands between messages are caught too. The config package reads `checkpoints`.
- `cog.rewind(threadId, toEntryId, options)` takes `RewindOptions` (`agents`, `memory`, `files`, `workspace`, `dryRun`, `force`) and returns a `RewindReport`: the `MemoryCascadeReport` with `conversation` (`rewound`, `cut`, `previousLeafId`), `files` (the restore result with the `entryId` whose checkpoint was restored and whether it is `exact`) and `runs` (`going`, `interrupted`, `paused`, `durable`). The files come from the checkpoint right after the point when only notes lie before the next user message, else from the nearest one before it. The message after the point is looked for on every branch of the thread, so a repeated rewind restores the same checkpoint. A checkpoint whose message could not be written is dropped. Files are restored first, so a rewind that fails leaves the conversation as it was. `dryRun` changes nothing and reports what would change, `MemoryCascade.rewind` takes `{ dryRun }` for it.
- `cog.forkThread(threadId, atEntryId, { newThreadId?, files?, workspace?, source?, agents?, force?, dryRun? })` forks a thread with its checkpoint references, and with `files` restores the fork's workspace to that point, copying the branch's checkpoints into it first when it is another workspace. `dryRun` returns a `ForkThreadPlan` without making the thread and leaves no copied checkpoint behind. Every check runs before the thread is made, so a refused fork leaves nothing, and a fork whose files fail to restore takes back the thread, its link and the copied checkpoints. `MemoryAdapter.forkThread` refuses a `newThreadId` that names a thread already, before it changes anything, and takes back a fork that fails on the way, deleting only the thread it made.
- A rewind or a fork with files holds the thread and the workspace for the whole operation (runs asked for meanwhile wait), refuses while runs of other threads work in the same workspace or commands of the workspace run (new `ErrorCode.WORKSPACE_BUSY`, 409), never forces past a durable run another process holds while files are restored, validates the restore with a dry run before `force` stops anything, checks that the checkpoint is one the workspace keeps for this thread and entry (forged references are refused), and takes a safety snapshot first (`files.safetySnapshotId`) so it can be undone. A tool call that goes on after its run stopped (regardless of its signal) keeps the workspace busy until it ends, and a forced rewind or fork waits for those calls (`toolSettleMs`), so a late write never lands over a restore. Runs on a side branch of the thread count as busy too, and so do runs in a workspace whose root holds the restored one or lies in it, also a root made later under a symlink. A restore that would change a file the safety snapshot could not keep (one it skipped, or one the workspace's own snapshot excludes leave out) is refused with `DENIED` before anything changes, snapshots honor `refuseHardLinks` (such files are skipped as `hard-link` and never read on restore), commands are refused while a restore changes the files, holds of a workspace are taken one at a time, a copy between stores marks the source store too, and remote restores leave alone everything under a skipped path. The safety snapshot covers every path the restore changes (the checkpoint's excludes, files as large as the largest one changed), and the checkpoint being restored is kept from the workspace's retention (`WorkspaceSnapshotOptions.protect`). Checkpoints follow the agent a run handed over to, approval hooks are raced against an abort like `onApproval`, and a tool asking to rewind its own run's thread gets a clear error. `cog.durableByDefault` says whether runs are durable by default.
- A run aborted while `onApproval` (or `guardrails.onToolApproval`) waits for an answer now ends with the abort instead of waiting for the answer.

CLI:

- `cogitator rewind <thread> [entry]` lists the active branch of a thread of the project's registry, entries with a file checkpoint marked, or rewinds it: the dry run first, then a prompt (`--yes` without a terminal), with `--files`, `--no-memory`, `--dry-run`, `--force`, `--agent`, `--registry` and `--json` (which needs `--dry-run` or `--yes`). It warns that only durable runs of other processes are seen, and falls back to the only registry agent with a workspace for a thread whose agent has no configured id.

Memory adapters (memory, test-utils):

- Every built-in adapter keeps a caller-given entry id (`NewMemoryEntry.id`, letters, digits, `_` and `-`, at most 128) and refuses an id it keeps already. The adapter conformance suite has the case `entry-named-id`.

Breaking changes and migration:

- `Workspace.restore(snapshotId, options?)` returns a `WorkspaceRestoreResult` instead of `void`. A workspace of your own that implements `restore` returns `{ snapshotId, dryRun, restored, deleted, unchanged, kept }` and honors `dryRun`, callers that ignored the result need no change.
- `WORKSPACE_SNAPSHOT_DEFAULT_EXCLUDE` is `['.cogitator/**', '**/node_modules/**', '**/.git/**']`, so snapshots of every workspace leave out installed dependencies and the git repository, and a restore leaves them alone. Install dependencies again after a restore that changed the lockfile, and use git itself for the repository.
- Remote workspace snapshots skip files over 10 MiB by default: pass `maxFileBytes` to `snapshot()` to keep larger ones.
- `cog.rewind()` drops the paused run and the durable runs of the thread (their checkpoints hold the conversation that was cut), so a paused run can no longer be resumed after a rewind of its thread. It refuses with `THREAD_BUSY` while a run goes on in the thread, here or as a durable run another process holds: wait for the run, or pass `force: true` to abort it first. It throws `VALIDATION_ERROR` for an entry that is not on the active branch before anything changes. The report it returns extends the `MemoryCascadeReport` it returned, so code that reads it needs no change.
- `addEntry` keeps a caller-given `id`: code that spreads an existing `MemoryEntry` into `addEntry` (to copy it) now keeps its id, which fails with "already exists" in the same adapter. Leave `id` out of the copy, as `forkThread` does.
- `ErrorCode` has a new member, `WORKSPACE_BUSY`: a `switch` over every code with no `default` needs a case for it.
- `cog.rewind()` and `forkThread()` with files refuse while a run of another thread works in the same workspace (`WORKSPACE_BUSY`), and refuse a checkpoint the workspace does not keep for the thread (`VALIDATION_ERROR`): pass the workspace the thread ran in, and `force` to stop the other runs.
- A memory adapter of your own that ignores `NewMemoryEntry.id` still works with checkpoints (the entry names its snapshot in metadata either way), but fails the new `entry-named-id` conformance case until it keeps the id.
