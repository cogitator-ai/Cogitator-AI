Forgetting a conversation now forgets what memory made of it. Every summary, memory item, fact, graph node and edge, vector and memory file keeps the entries it stands on, and deleting, redacting or rewinding those entries follows that lineage into every store, so a user who asks to be forgotten is not remembered through a fact or a playbook rule written from what they said.

- Core: `Cogitator.forget({ entryIds } | { threadId } | { userId }, { agents?, graph?, keepReplies? })` deletes entries, a thread, or every thread of a user (by its `metadata.userId`) and everything kept for the user, with all memory derived from them. `Cogitator.redactEntries(entryIds, { agents?, graph?, keepReplies?, reason? })` replaces what entries said with `[redacted]` while they keep their place in the thread, and takes away what was derived from them the same way. `Cogitator.rewind(threadId, toEntryId, { agents?, graph? })` rewinds a thread, and the memory items that stood only on the entries after `toEntryId` become `stale`. Each returns a `MemoryCascadeReport`. Items, files and facts are kept by the memory id of an agent, so every run now names its agent in the thread's `metadata.memoryAgentIds`, and a cascade goes through the memory of the agents a thread names and of its owner. `agents` (agents or their memory ids) adds others, and is needed for a thread written before threads named their agents and for a user without threads: without it such a call throws `VALIDATION_ERROR`. `graph` is a knowledge graph of your own to go through too. `MemoryCascadeCall` is the type of these options.
- Core: memory extraction and compaction after a run stop before their next model call once the run's branch is no longer the thread's active one, such as after a rewind or a checkout while they work, so nothing is learned or summarized from a branch the conversation left. Extraction also writes nothing a window's answer gave once the branch was left, and drops the items whose entries were forgotten or redacted while the model answered.
- Memory: `MemoryExtractor.extract` takes `beforeWindow(own)`, which stops the extraction before a window's model call when it returns `false`, and `beforeWrite(items)`, which returns the items of a window to write.
- Memory: `MemoryCascade` (`deleteEntries`, `redactEntries`, `deleteThread`, `deleteUser`, `rewind`) does the work over the stores it is given (`{ memory, items?, files?, graph?, facts?, embeddings? }`) for the agents in `{ agentIds, keepReplies? }`. With deleted or redacted entries go the compaction summaries that cover them (the entries before `firstKeptEntryId` on their branch) or quote them in an atom, so the next compaction writes them again, the memory items, facts and graph nodes and edges that stand only on them (those that stand on more lose the quotes of them), the vectors of the entries, the summaries and the facts that go (deleted from `embeddings` by source, whether or not a message index listens), the memory file versions written at them, and every version of an observation or a playbook that names an item or a lesson that went. A playbook in front is first written again without the rules that stood on such a lesson, and an observation is written again over its redacted file by the next refresh. A user message takes its replies (the entries after it on every branch up to the next user message, events such as a model change or an approval among them), as an answer may say again what it said, unless `keepReplies`. A rewind called again once the thread stands at `toEntryId`, such as after a failure, marks what stood only on the entries after it. `deleteThread` also purges the items and entities and redacts the memory file versions kept for the thread alone, and `deleteUser` those of the user's scope, and deletes the facts and graph nodes and edges whose `metadata.userId` is the user and the embeddings with that metadata (`deleteByFilter`).
- Memory: every built-in adapter (in-memory, SQLite, Postgres, Redis, MongoDB) has `redactEntry(entryId, { at, reason? })`: the entry's text, the arguments of its tool calls and the results of its tools become `[redacted]`, its place, role and call ids stay, `metadata.redacted` records when and why, an event entry such as a compaction is refused, and a missing entry gives `null`. Change listeners hear `{ type: 'entry-redacted', entryId, threadId }`, and the message index drops the entry's vectors. `redactedEntry` and `REDACTED_TEXT` are exported for an adapter of your own. `MemoryItems.reviseEvidence(itemIds, keep)` keeps the evidence pieces `keep` takes and returns the ids it changed.
- Types: `MemoryAdapter.redactEntry?`, `EntryRedaction` (`at`, `reason?`), and `entry-redacted` among the `MemoryChange` events.
- Test utils: the memory adapter conformance suite checks `redactEntry` in the scenario `redacts-an-entry-in-place`.
