Subagents and commands from Markdown files in Claude Code's format, approvals of delegated runs that bubble up through nested checkpoints, background subagents, and agent teams in swarms with a live graph in Studio.

Everything is off by default: without `subagents`, `commands` and the `team` strategy a run does what it did before, and `agentAsTool()` still declines the approvals of its inner agent.

Breaking:

- `ToolAccess.agent` may now be a function that reads the agent's name from the call's arguments (`agent: (params) => params.subagent_type`), so an `Agent(name)` rule matches a tool that delegates to the agent its call names. Code that reads `tool.access.agent` as a string checks `typeof agent === 'string'` first.
- The Claude Code names `SendMessage`, `TaskOutput` and `TaskStop` used to match no tool. They now name `send_message`, `task_output` and `task_stop`, so a rule or hook matcher with one of them that matched nothing before matches these tools.
- An entry of a YAML `allowed-tools` list in a `SKILL.md` is split on white space and commas outside parentheses, as a string value always was: `- Read Grep` is two tools. `Bash(git status *)` stays one.
- In swarms, a tool of `agentTools` named like a tool of the strategy gives way to the strategy's tool. Only the new team tools can collide.

New:

- `CogitatorConfig.subagents: { files?, agents?, approvalMode?, tools?, maxDepth?, maxBackground?, messages?, mcp?, onDelegationStart?, onDelegationComplete?, onDiagnostic? }`. Subagents come from Markdown files (`.agents/agents`, `.cogitator/agents`, `.claude/agents` of the project, read only once it is trusted as for hooks, the user's `~/.agents`, `~/.cogitator` and `~/.claude` folders, the managed directories, the host's `dirs`, folders read recursively) and from `agents` in code, shaped like Claude Code's `--agents` JSON. Precedence is managed, code, `dirs`, project, user. The frontmatter is read leniently with the skills' YAML parser: `name`, `description`, `tools`, `disallowedTools`, `model` (`inherit`, an alias of the new `llm.modelAliases`, or `provider/model`), `permissionMode` (`manual` is `default`), `maxTurns` (the subagent's `maxIterations`), `skills` (preloaded in full), `mcpServers` (names of servers the run has, or inline ones connected through `subagents.mcp`), `hooks` (`Stop` runs as `SubagentStop`), `memory` (`user`, `project`, `local`: a notes folder at Claude Code's place with an `agent_memory` tool and `MEMORY.md` in the prompt), `background`, `isolation: worktree`, `color` and `effort`. A file without frontmatter or `name` is documentation, problems are diagnostics (`DefinitionDiagnostic`) logged once.
- Runs get an `agent` tool with Claude Code's `Agent` input (`description`, `prompt`, `subagent_type`, `model`, `run_in_background`, `name`), or a tool per subagent with `tools: 'each'`, plus `send_message`, `task_output` and `task_stop`. `AgentConfig.subagents` (`false` or a list of names) limits which subagents an agent may use, and it is not carried by the agent wire. A subagent gets the delegating run's permission mode and `session` rules, its own `permissionMode` only narrows that mode (`narrowMode()`), `Agent(name)` deny rules refuse it, its tool calls are charged to the session of the run that delegated, `tools` and `disallowedTools` filter every tool of its run with the permission rule grammar, and a `tools` list that names none of the available tools fails the delegation. `maxDepth` (3) caps nesting.
- `approvalMode: 'bubble'` (in `subagents` and in `agentAsTool()` options): the delegate's approvals go to the calling run's `onApproval`, and when the delegate pauses, for an approval or a question of a tool, the calling run pauses with the delegate's checkpoint in `RunCheckpoint.turn.children[toolCallId]` and its interrupts and approvals under ids that start with `<toolCallId>/`, across any number of levels. A resume that answers them (`responses` or `decisions`) goes on inside the delegate, with its calls checked against the permission rules again. Tools that delegate get `ToolContext.delegation` (`conversation()`, `onApproval`, `resume`, `depth`), and `DelegatePauseSignal` pauses the calling run.
- Background subagents run on their own run handle: `send_message` steers a running one or continues one that finished with its conversation, `task_output` reads its result, `task_stop` stops it. A run that would stop waits for the background subagents it started and reads their results as a `<task-notification>` message, a run that pauses or fails stops them. `maxBackground` (20) caps how many run at once.
- `isolation: worktree` runs a subagent in a git worktree under `.cogitator/worktrees/` of the repository the run's local workspace is in, removed with its branch when the subagent changed nothing and kept, with its path in the result's `note`, otherwise. A subagent that paused goes on in the same worktree.
- `messages: 'none' | 'conversation' | (messages) => messages` picks the delegating run's messages a delegate reads before its task. `onDelegationStart` and `onDelegationComplete` hear every delegation (`DelegationStartEvent`, `DelegationCompleteEvent`), and the runtime's `SubagentStart` and `SubagentStop` hooks fire for every subagent run.
- `CogitatorConfig.commands: { files?, commands?, onDiagnostic? }`. An input that starts with `/name` is replaced by the command's template before the run starts (never in a run started from a tool call): Markdown files in `commands/` folders from the same places as subagents (`frontend/component.md` is `/frontend:component`) and templates in code. `$ARGUMENTS`, `$ARGUMENTS[N]` and `$N` (0-based, as Claude Code counts them now), `$name` of `arguments`, `\$` escapes, `${CLAUDE_PROJECT_DIR}`, `${COGITATOR_PROJECT_DIR}` and `${CLAUDE_SESSION_ID}`, and `ARGUMENTS: <value>` added when no placeholder took the arguments. `allowed-tools` become allow rules of that run when permissions are set up, `model` runs it on another model. `RunResult.command` reports what was expanded (`ExpandedCommand`).
- `cog.listSubagents({ root })` and `cog.listCommands({ root })` return what a run would see, with the diagnostics.
- `@cogitator-ai/core` exports `parseSubagentFile`, `parseCommandFile`, `SubagentFinder`, `CommandFinder`, `toolPolicy`, `narrowMode`, `taskNotification`, `openWorktree`, `agentMemoryDir`, `commandInvocation`, `expandCommand`, `splitArguments`, `DelegatePauseSignal`, `isDelegatePause` and the tool names. `@cogitator-ai/types` adds `SubagentsConfig`, `SubagentDefinition`, `SubagentDefinitionInput`, `SubagentCatalog`, `DefinitionFileOptions`, `DefinitionDiagnostic`, `DelegationApprovalMode`, `DelegationMessages`, the delegation events, `ToolDelegationContext`, `DelegatedResume`, `CommandsConfig`, `CommandDefinition`, `ExpandedCommand` and `BackgroundSubagentStatus`. `@cogitator-ai/config` reads `subagents`, `commands` and `llm.modelAliases` from config files (without the functions).
- Agent teams: a new `team` swarm strategy where a lead plans the work as a shared task list and members claim or are assigned tasks, work through them concurrently and talk through mailboxes, in the spirit of Claude Code's agent teams. Tasks are pending, in progress or completed, can depend on other tasks, and are claimed atomically, with one task in progress per member. The lead gets `create_task` and `assign_task`, everyone gets `list_tasks`, `update_task`, `send_message` and `read_inbox`, and members get `claim_task`. Messages are marked as coming from agents and never count as the user's approval, and every bound (`maxLeadTurns`, `maxTurnsPerMember`, `maxConcurrentMembers`, `maxTasks`) keeps a run finite. `SwarmBuilder` gets `.lead()`, `.members()` and `.team()`. `@cogitator-ai/types` adds `TeamConfig`, `TeamTask`, `TeamResult` and the typed `team:*` events (`TeamEventMap`).
- `@cogitator-ai/studio` runs the swarms of a project (`POST /api/swarms/:key/run`, a Swarms page) and shows a team as a live graph: the agents' status, task assignments, messages and the task board.
