---
title: Resumable Streams
description: Let a client that lost the stream of an agent run reconnect with Last-Event-ID, replay what it missed and follow the run to its end.
---

A streamed agent run can take minutes. A flaky network, a phone that switches cells or a laptop that goes to sleep cuts the SSE connection, and by default the adapter then stops the run. With `resumableStreams` the run goes on without the client, every event is kept, and the client reconnects to pick the stream up exactly where it stopped.

It works the same in every adapter: Express, Fastify, Hono, Koa, Tetsu and the Next.js handlers, on `/agents/:name/stream` and `/agents/:name/resume/stream`.

## Turn it on

```typescript
// Express
new CogitatorServer({ app, cogitator, agents, config: { resumableStreams: true } });

// Fastify
await fastify.register(cogitatorPlugin, { cogitator, agents, resumableStreams: true });

// Hono and Koa
cogitatorApp({ cogitator, agents, resumableStreams: true });

// Tetsu
cogitatorController({ cogitator, agents, resumableStreams: true });

// Next.js
export const POST = createChatHandler(cogitator, agent, { resumableStreams: true });
```

`true` keeps the events in the memory of the process with the default limits. An object sets them:

| Option              | Default   | What it does                                                                           |
| ------------------- | --------- | -------------------------------------------------------------------------------------- |
| `maxEvents`         | `1000`    | Events kept of each stream. Past it the oldest are evicted                             |
| `retentionMs`       | 5 minutes | How long a finished stream stays replayable                                            |
| `maxStreams`        | `1000`    | Streams kept at once. A new one evicts the stream that finished first, else the oldest |
| `detachedTimeoutMs` | 5 minutes | How long a run goes on with no client following its stream before it is stopped        |
| `store`             | in-memory | Where the events are kept, see [Several processes](#several-processes)                 |

Off by default: events carry no ids and a client that disconnects stops the run, as before.

## Event ids

Every event frame of a resumable stream carries an SSE `id`:

```
id: stream_6f1c2b7e-3a4d-4e8f-9b0a-1c2d3e4f5a6b:3
data: {"type":"text-delta","id":"txt_1","delta":"Hel"}
```

The id is `<streamId>:<seq>`. The stream id is random and cannot be guessed, the sequence number starts at 1 and grows by one with each event, so the id alone names the stream and the place in it. Heartbeat comments carry no id.

## Reconnect

Send the same route again with the id of the last event the client got, in the `Last-Event-ID` header or the `lastEventId` query parameter:

```typescript
const res = await fetch('/cogitator/agents/assistant/stream', {
  method: 'POST',
  headers: { 'Last-Event-ID': lastEventId },
});
```

The request starts no run and its body is not read. The answer replays the events after that id, with their ids, then follows the run live until `finish` (and `data: [DONE]`) or `error`. Several clients may follow the same stream at once.

| Case                                                                 | Answer                                                  |
| -------------------------------------------------------------------- | ------------------------------------------------------- |
| A stream of the caller                                               | `200`, the events after the id, then the live ones      |
| An unknown or expired stream, another user's, or an id it never sent | `404 STREAM_NOT_FOUND`, before any SSE header           |
| An id that is not `<streamId>:<seq>`                                 | `400 INVALID_INPUT` (Tetsu: `422 VALIDATION_FAILED`)    |
| Events after the id were evicted                                     | `200` with one `error` event `STREAM_RESUME_GAP`, no id |

Only the user who started the stream may reconnect to it, as the adapter's `auth` identifies them. An anonymous caller may reconnect only to a stream an anonymous caller started. On `STREAM_RESUME_GAP` the client should fetch the thread (`GET /threads/:id`) to catch up, the message names the thread.

In Next.js the reconnect is the same request again, body included: `beforeRun` identifies the caller from the request and its input. `useCogitatorChat` does all of this by itself, see [Next.js](/docs/integrations/nextjs#reconnecting).

## Detached runs

When the last client leaves, the run goes on and its events keep going into the store. If nobody reconnects within `detachedTimeoutMs`, the run is stopped, so a client that never comes back does not run up cost. Its stream then ends with an `error` event `STREAM_ABORTED`, which a late reconnect still gets. In Tetsu the `until` signal stops these runs too when the server drains, and in Next.js so does the `signal` `beforeRun` returns.

## Several processes

The default store lives in the memory of one process. Behind a load balancer, a reconnect may land on a process that did not start the run. Give every process one shared `store`, an implementation of `StreamReplayStore` from `@cogitator-ai/server-shared`:

```typescript
import type { StreamReplayStore } from '@cogitator-ai/server-shared';

const store: StreamReplayStore = {
  create: (stream) => redisCreate(stream),
  append: (streamId, entry) => redisAppendAndPublish(streamId, entry),
  read: (streamId, afterSeq) => redisRead(streamId, afterSeq),
  finish: (streamId) => redisFinishAndPublish(streamId),
  get: (streamId) => redisGet(streamId),
  subscribe: (streamId, subscriber) => redisSubscribe(streamId, subscriber),
};

cogitatorApp({ cogitator, agents, resumableStreams: { store } });
```

- `read` answers the events after a sequence number, whether some were evicted (`gap`) and whether the stream finished.
- `subscribe` must reach subscribers on every process, which takes pub/sub (Redis `PUBLISH`/`SUBSCRIBE` or similar), and deliver events in order.
- `get` reports `subscribers` across every process: a run checks it before it stops as detached, so a client following it on another process keeps it going.

The limits `maxEvents`, `retentionMs` and `maxStreams` belong to the in-memory store, next to a `store` of your own they throw.

## WebSocket

The WebSocket endpoints do not resume. Their frames use their own vocabulary (`token`, `tool-call`, `complete`, `cancelled`) rather than the stream protocol the store keeps, and a run lives as long as its socket: closing it or sending `stop` cancels the run. Use the SSE routes for runs a client must be able to resume.
