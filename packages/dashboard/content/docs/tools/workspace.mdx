## Overview

A `Workspace` is the directory an agent works in. It reads, writes, lists and runs commands, and every path it takes is relative to its root: `..`, an absolute path elsewhere and a symlink that points out are refused with a `WorkspaceError` of code `OUTSIDE_ROOT`.

Two implementations ship:

- `LocalWorkspace` from `@cogitator-ai/core`: a directory of this machine, commands run as your process.
- `DockerWorkspace` from `@cogitator-ai/sandbox`: the same files, commands run in one long-lived container.

Hand a workspace to an agent (or to one run) and the tools get it as `context.workspace`. `workspaceTools()` gives the agent `read_file`, `write_file`, `edit_file`, `list_files`, `glob`, `grep` and `exec` on top of it.

```typescript
import { Agent, Cogitator, LocalWorkspace, workspaceTools } from '@cogitator-ai/core';

const workspace = new LocalWorkspace({ root: './project' });
await workspace.start();

const coder = new Agent({
  name: 'coder',
  model: 'anthropic/claude-sonnet-5-5',
  instructions: 'You fix bugs in the project. Read files before you edit them.',
  tools: workspaceTools(),
  workspace,
});

const cog = new Cogitator();
await cog.run(coder, { input: 'The parser test fails, find out why and fix it' });

await workspace.dispose();
```

## Lifecycle

Whoever creates a workspace owns it: call `start()` before the first run and `dispose()` when you are done. The runtime only uses the workspace it is given, it never starts or disposes one. `LocalWorkspace` holds nothing, so it also starts itself on first use, while `DockerWorkspace` must be started, since `start()` creates its container.

## Agent or run

`AgentConfig.workspace` is the agent's default, `RunOptions.workspace` replaces it for one run, which is how one agent serves many projects or users:

```typescript
await cog.run(coder, { input: 'Bump the version', workspace: workspaceFor(user) });
```

After a handoff, the agent the run went on as brings its own workspace, unless the run set one. `invokeTool(tool, args, { workspace })` passes one to a tool called outside a run. Like `deps`, a workspace is not kept in a paused run's checkpoint, so pass it again to `resume()`.

## The interface

| Member                                 | What it does                                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `id`, `root`, `cwd`                    | Stable id, absolute root, current directory relative to the root (`.` by default)                      |
| `start()`, `dispose()`                 | Prepare and release, both idempotent                                                                   |
| `contains(path)`                       | Whether a path lies inside the root once symlinks are followed, never throws                           |
| `read`, `readBytes`, `write`           | Text (UTF-8) or bytes, with a size limit (`maxBytes`, 10 MiB by default for `LocalWorkspace`)          |
| `list(path, { recursive, glob, ... })` | Entries with type, size and modification time, symlinked directories listed but not entered            |
| `stat`, `exists`, `mkdir`, `rename`    | What their names say, `rename` refuses to replace an entry unless `overwrite` is set                   |
| `remove(path, { recursive, trash })`   | Deletes, or with `trash: true` moves the entry to `.cogitator/trash/<time>/` inside the root           |
| `exec(command, options)`               | `sh -c` in `cwd` or `options.cwd`, streaming `onStdout`/`onStderr`, `timeout`, `signal`, capped output |
| `snapshot()`, `restore(id)`            | Optional: record the files and go back to them                                                         |

`exec` resolves with `{ stdout, stderr, exitCode, timedOut, truncated, durationMs }`, also for a non-zero exit or a timeout (exit code 124), and rejects with code `ABORTED` when its signal aborts. A timeout or an abort kills the command and every process it started.

Every failure is a `WorkspaceError` with a `code`: `OUTSIDE_ROOT`, `NOT_FOUND`, `NOT_A_FILE`, `NOT_A_DIRECTORY`, `EXISTS`, `NOT_EMPTY`, `TOO_LARGE`, `INVALID_PATH`, `NOT_STARTED`, `DISPOSED`, `UNAVAILABLE`, `ABORTED`, `UNSUPPORTED` or `IO`.

```typescript
import { WorkspaceError } from '@cogitator-ai/core';

try {
  await workspace.read('../secrets.env');
} catch (error) {
  if (WorkspaceError.is(error, 'OUTSIDE_ROOT')) console.log('refused');
}
```

## LocalWorkspace

```typescript
const workspace = new LocalWorkspace({
  root: './project',
  cwd: 'packages/api', // commands run here by default
  maxFileBytes: 5 * 1024 * 1024,
  exec: {
    timeout: 60_000,
    maxOutputBytes: 512 * 1024,
    env: { CI: 'true' },
    inheritEnv: ['PATH', 'HOME', 'NODE_OPTIONS'],
  },
});
```

| Option                | Default                   | What it does                                                      |
| --------------------- | ------------------------- | ----------------------------------------------------------------- |
| `root`                | required                  | The directory the workspace is confined to                        |
| `cwd`                 | `.`                       | Current directory, relative to the root                           |
| `create`              | `true`                    | Create the root when missing                                      |
| `maxFileBytes`        | 10 MiB                    | Largest file `read` and `write` accept                            |
| `exec.shell`          | `/bin/sh`                 | The shell commands run with                                       |
| `exec.timeout`        | 120000                    | Milliseconds before a command is killed                           |
| `exec.maxOutputBytes` | 1 MiB                     | Bytes of stdout and of stderr a result keeps                      |
| `exec.env`            | none                      | Variables every command gets                                      |
| `exec.inheritEnv`     | `WORKSPACE_INHERITED_ENV` | What commands inherit from your environment, `true` for all of it |

By default a command inherits only what a shell needs (`PATH`, `HOME`, the locale and a few more, see `WORKSPACE_INHERITED_ENV`), so the API keys in your environment do not reach commands the model writes.

### How paths are guarded

A path is resolved with every symlink followed, a dangling one too (writing through a dangling link would create its target), and refused when it lands outside the root. Files are then opened with `O_NOFOLLOW` and checked again once open: the path must still resolve inside the root, to the very file that was opened. A symlink swapped in between the check and the open is caught, for a file and for a parent directory. A symlink a command creates is refused like any other when the file API reads it.

What the guard does not stop:

- A hard link inside the root to a file outside it is that file, hard links cannot be told from the original.
- A race that swaps a parent directory for a symlink right before a write or `mkdir` can leave an empty new file or directory outside the root, never content.
- `exec` runs as your process, only its directory is confined: `cat /etc/passwd` works. Use `DockerWorkspace` for commands you do not trust.

### Snapshots

`LocalWorkspace` does not implement `snapshot()` and `restore()`. Copying the tree for every checkpoint is too slow for real projects, so they wait for a content-addressed store that keeps each version of a file once. The snapshot type already has what a checkpoint per user message needs: an `id`, the `workspaceId`, `createdAt`, a `label` (such as the message id) and your own `metadata`.

## DockerWorkspace

`DockerWorkspace` runs commands in a container while the files stay on your machine: the root of a host workspace is bind-mounted at `/workspace`, files are read and written through the host workspace (so its guard applies), and commands run with `docker exec` in the matching directory of the container.

```typescript
import { LocalWorkspace } from '@cogitator-ai/core';
import { DockerWorkspace } from '@cogitator-ai/sandbox';

const workspace = new DockerWorkspace({
  host: new LocalWorkspace({ root: './project' }),
  image: 'node:24-alpine',
  resources: { memory: '1GB', cpus: 2, pidsLimit: 256 },
  network: { mode: 'bridge' }, // default: no network
});
await workspace.start();
try {
  await cog.run(coder, { input: 'Run the tests and fix what fails', workspace });
} finally {
  await workspace.dispose();
}
```

One container serves the whole workspace: it is created in `start()`, kept between commands (installed packages and build output stay), and removed in `dispose()`, which also disposes the host workspace it owns. It has the [sandbox defaults](/docs/deployment/sandbox#security-defaults): no capabilities, no new privileges, a PID limit and no network unless `network` allows it. On Linux commands run as your uid and gid, so the files they write stay yours. A timeout or an abort kills the command and what it started, the container keeps running. Without Docker, `start()` fails with code `UNAVAILABLE`.

| Option           | Default            | What it does                                 |
| ---------------- | ------------------ | -------------------------------------------- |
| `host`           | required           | The workspace whose root is mounted          |
| `image`          | `alpine:3.19`      | Image of the container, pulled when missing  |
| `workdir`        | `/workspace`       | Where the root is mounted                    |
| `resources`      | none               | `memory`, `cpus`, `cpuShares`, `pidsLimit`   |
| `network`        | `{ mode: 'none' }` | `mode` and `dns`, `allowedHosts` is refused  |
| `mounts`         | none               | More bind mounts                             |
| `env`, `user`    | none, your uid     | Environment and user of commands             |
| `docker`         | the CLI's socket   | How to reach the daemon                      |
| `timeout`        | 120000             | Milliseconds before a command is killed      |
| `maxOutputBytes` | 1 MiB              | Bytes of stdout and of stderr a result keeps |

## workspaceTools

`workspaceTools(workspace?, options?)` returns the tools. Each call uses the workspace passed here, else the run's (`context.workspace`), and fails with a clear error when there is none, so one tool set serves every workspace.

| Tool         | What it does                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| `read_file`  | Text by line range: `offset` (1-based) and `limit` (default 2000 lines), `nextOffset` when more lines follow |
| `write_file` | Replaces a file's content, creating it and its directories                                                   |
| `edit_file`  | Replaces `oldString` with `newString`, which must appear exactly once unless `replaceAll` is set             |
| `list_files` | A directory's entries, optionally recursive, at most 1000                                                    |
| `glob`       | Files matching a pattern such as `**/*.ts`, at most 1000                                                     |
| `grep`       | Lines matching a regular expression, binary files and files over 1 MiB skipped, at most `maxMatches`         |
| `exec`       | A shell command through `workspace.exec`, killed when the run is cancelled                                   |

| Option            | Default                | What it does                                              |
| ----------------- | ---------------------- | --------------------------------------------------------- |
| `tools`           | all                    | Only these tools, e.g. all but `exec`                     |
| `requireApproval` | `exec` only            | Which tools wait for an [approval](/docs/tools/approvals) |
| `skipDirs`        | `.git`, `node_modules` | Directories `list_files`, `glob` and `grep` skip          |
| `execTimeout`     | the workspace's        | Timeout of `exec` when the call sets none                 |

```typescript
const reviewed = workspaceTools(undefined, {
  tools: ['read_file', 'list_files', 'glob', 'grep', 'write_file', 'edit_file'],
  requireApproval: (name) => name === 'write_file' || name === 'edit_file',
});
```

The global `file_read`, `file_write` and `exec` [built-in tools](/docs/tools/built-in) and `restrictFileTools` stay as they are. The workspace tools are a factory, like the memory tools, not part of `builtinTools`.

## Long tool results

A tool result longer than the tool's `maxResultLength` (or `limits.maxToolResultLength`, 100,000 characters by default) is cut for the model. When the run has a workspace, the full text is saved first to `.cogitator/tool-results/<runId>/<toolCallId>.txt`, and the model gets the cut preview with a note naming the file and telling it to page through it with `read_file`. `toolResultPath(runId, toolCallId)` gives the same path in your code. Without a workspace nothing changes, and when saving fails the result is only cut, with a warning in the log. See [context management](/docs/advanced/context-management#long-tool-results).
